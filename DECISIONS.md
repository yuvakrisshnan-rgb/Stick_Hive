## 2026-10-03 — Direct UPI orders now confirm themselves automatically for Google Pay; the customer-facing manual-claim button is gone

**Explicit project-owner override of a prior, more conservative safety decision.** `checkGooglePayPayment` (`backend/payments/google-pay.ts`) already polled Google's real Pay-for-Business merchant API (`nbupaymentsmerchants` scope, `merchantTransactions:get`) every ~10 seconds from `order-success/page.tsx`, and already got back a genuine transaction status + amount for the order's own UPI transaction reference. By the original design, that check only ever wrote a `payment_auto_verification` *suggestion* column for an admin to review - its own comment said plainly it "must never itself mark an order paid." The project owner explicitly overrode that, with full knowledge of the trade-off below, and asked for Google's confirmation to mark the order paid directly instead - the customer-facing "I've Paid — Check Payment" self-report button is removed entirely, not replaced with anything.

**What changed**:
- New `confirmUpiPaymentViaGooglePay` (`backend/orders/service.ts`, right after `setRazorpayPaymentState`, deliberately mirroring its exact shape) is the new automated path allowed to mark a direct-UPI order "paid" - idempotent on the same `payment_status != 'paid'` guard, same `awaiting_payment` → `placed` status transition, writes a real `payment_verification` record (not the old suggestion-only `payment_auto_verification`, which this now clears). `verifiedBy` is set to the literal string `"google_pay_auto"` rather than an admin's email - every other `paymentVerification` record has a real admin address there (`normalizePaymentVerification`), so this is immediately, visibly distinguishable in the admin dashboard (`admin-client.tsx` already just renders `"Verified by {verifiedBy}"` as-is - no admin UI changes were needed at all).
- `checkGooglePayPayment` calls this new function instead of writing the suggestion column, and - mirroring the Razorpay webhook route's exact pattern - sends the existing order-confirmation email itself, gated on the write actually having transitioned the order for the first time (`!alreadyProcessed`), so a repeat poll against an already-paid order never re-sends it.
- `order-success/page.tsx`: removed the "I've Paid — Check Payment" button, `isClaimingPayment` state, and `handleClaimUpiPayment` entirely. `paymentMessage` state stays - it's also used by the unrelated "Pay Again" expired-window retry flow (`handleRetryPayment`), confirmed by checking every other usage before touching it. The existing 10-second payment-sync poll (unchanged) and the page's existing `paymentStatus`-driven rendering (unchanged) are what pick up the new "paid" state - no new polling or rendering logic needed, since the only thing that changed is what the poll's own backend call now *does* once it detects success.
- `/api/orders/[orderId]/payment-claim` and `claimUpiPayment` (`backend/orders/service.ts`) are left in place as dead code, not deleted - same convention already used for the dead Stripe/Razorpay checkout-page code in this project, in case a manual claim step is ever reinstated.
- Checkout and order-success copy updated to stop implying a uniform manual-or-instant confirmation step for every UPI payer - both now say plainly that Google Pay confirms automatically and any other UPI app is confirmed once the bank statement is reconciled, rather than a vaguer "we verify your payment" that no longer has a customer-facing action attached to it.

**The accepted trade-off, stated plainly, not an oversight**: any UPI payment made via an app other than Google Pay (PhonePe, Paytm, a bank app, BHIM, etc.) now has **zero automated confirmation signal and no customer-facing way to flag it either** - the claim button is gone, by explicit choice, with no fallback added back. An admin must notice and manually reconcile those from the bank statement against pending orders (`updateAdminOrder` / the admin UI's manual-verify modal, unchanged, still fully functional). `backend/admin/insights.ts`'s "stuck UPI payment" alert is keyed entirely off `payment_claimed_at`, which only the now-dead claim button ever set - it will never fire for a new order again (still correctly covers any pre-existing historical order already in that state). Logged in BACKLOG.md as a known, deliberate consequence, not a bug.

**How big is that gap, really? Researched, not assumed - and genuinely inconclusive from Google's own public docs.** Checked four separate Google Pay for India developer-docs pages (`get-transaction-details`, `googlepay-business`, `prerequisites`, plus the general omnichannel overview) and two targeted searches, specifically asking whether `merchantTransactions:get` only sees payments made through the Google Pay app, or any UPI payment landing in the merchant's registered VPA regardless of which app the payer used. **Google's documentation does not say, explicitly, either way** - every page fetched either omitted the distinction entirely or stated outright that the scope "is not explicitly specified" in the available content. Two things worth weighing against that gap:
- This app's own QR/deep-link (`getUpiPaymentDetails`) is a plain, standard `upi://pay?...&tr=...` intent URI - openable by any UPI app - never routed through Google's own `merchantPayments:initiate` payment-*initiation* API. So if Google does see this, it's acting as the merchant's registered receiving-side PSP for that VPA (the way Razorpay/Cashfree/etc. do), not because Google itself brokered the payment.
- The API is explicitly named "omnichannel" and Google's own copy describes it as letting a merchant "request and accept UPI payments from customers on any platform" (web/iOS/PWA) - about the merchant's *channel*, and the response's `paymentMode` field is documented to just say the generic `"UPI"`, not anything Google Pay-specific - both mild, non-conclusive signals toward "sees the whole VPA," not "Google Pay app only."
- Set against that: Google Pay for Business requires a real, formal merchant-onboarding relationship with Google (a `googleMerchantId`, "you're contacted by the Google Business Team") - whether this project's actual registered VPA (`STICKHIVE_UPI_ID`) has that relationship, and what it actually covers, is a real-world business-account fact no amount of reading public docs can confirm from here.
- One of the fetched pages' own content explicitly recommended the same thing: contact Google's own point of contact for a definitive answer on exactly this question, since even their documented test-endpoint details require direct outreach.

**Net effect on the stated gap**: if Google's visibility is VPA-wide (the mildly-favored reading above), the real gap is narrower than "only Google Pay" implies - some non-Google-Pay-app payments might already auto-confirm too, discovered as a pleasant side effect rather than assumed. If it's truly Google Pay app-only, the gap is exactly as described. Either way, the code change itself doesn't need to change based on the answer - `checkGooglePayPayment` already only fires for whatever Google's API actually reports back, confirmed or not, so nothing was built assuming the more generous interpretation. Worth getting a real, authoritative answer from Google's own merchant support channel before this trade-off gets relied on for a meaningful order volume.

**Verified via**: full pre-push gate (`tsc --noEmit`, `next build`, `build:vinext`, `eslint` on touched files, `test:unit` - 26/26) clean. No real `GOOGLE_PAY_MERCHANT_ID`/`GOOGLE_PAY_SERVICE_ACCOUNT_JSON` test credentials were available in this environment, so the actual Google API call itself (`checkGooglePayPayment`'s `fetch` to `nbupayments.googleapis.com`) was not exercised against a real Google response - that remains genuinely untested end-to-end and should be run for real the next time real credentials are available. What *was* verified live, for real, without needing those credentials: placed a real order through the full signed-in checkout flow (no "I've Paid" button anywhere, confirmed via `page.getByRole("button", {name: /i.ve paid/i}).count() === 0`), then - simulating exactly what `confirmUpiPaymentViaGooglePay` does, same SQL shape, run directly against the same local D1 the dev server uses - flipped the order to `paid` out-of-band while the order-success page sat open and untouched. The page's own existing 10-second poll picked up the change and re-rendered to "Order Confirmed!" within 6.1 seconds, with zero manual action, zero reload, zero button click - proving the actual thing this change exists to deliver (the frontend side) rather than just reading the code and assuming it. Separately signed in as the configured admin (`STICKHIVE_ADMIN_EMAILS`) and confirmed the same order renders correctly in the admin dashboard: `PAYMENT · UPI`, `Paid`, a "Verified payment" box showing the real transaction/UTR/amount, and `Verified by google_pay_auto` - clearly distinguishable from a human admin's email, exactly as intended - with the fulfillment dropdown and shipping-details section both working normally, confirming a Google Pay-confirmed order needs no special handling to flow through the rest of the admin UI.

## 2026-10-02 — Checkout payment method corrected: Razorpay reverted to direct UPI

The entry directly below this one ("Checkout: sign-in required, Razorpay-only, auto-launched payment") shipped with Razorpay as the payment method. That was tried deliberately, specifically to make payment confirmation fully automatic - a signed webhook marking an order paid with no admin step, instead of an admin eyeballing a shopper's self-reported "I've Paid" claim. After it landed, the decision changed: go back to direct UPI (QR code + deep link, paid straight to the store's own VPA, no payment gateway in between) instead of Razorpay. The sign-in gate and the email-verify removal from that entry are unaffected and stay exactly as they were - only the payment-method pieces were corrected.

**This is a deliberate, known trade-off, not an oversight**: direct UPI has no gateway sitting in the middle, so there is no automated way to confirm payment server-side. An admin still has to manually verify a shopper's self-reported "I've Paid" claim via the existing `claimUpiPayment`/`updateAdminOrder` paths - exactly as it worked before any of this checkout work started. Choosing UPI over Razorpay means explicitly choosing to keep that manual step, in exchange for not depending on a third-party payment gateway at all.

**The "go straight to payment, not an order-received page" goal survives the correction, but is satisfied differently.** Razorpay needed a ref-guarded `useEffect` on `order-success/page.tsx` to auto-launch its `checkout.js` modal, because Razorpay's own payment UI only appears after that explicit launch call. Direct UPI doesn't have an equivalent "click to start" step at all - the QR code and deep link already render immediately once the page loads a `paymentMethod: "upi"` order with `upiPayment` details (pre-existing backend logic in `backend/orders/service.ts`, never touched by any of this checkout work). So the auto-launch effect was removed entirely, not adapted - UPI never needed it. The actual remaining fix was in `order-success/page.tsx`'s copy: its heading/description used to say "Order Received" unconditionally for a non-Razorpay order, which is misleading for an order that's actually still awaiting payment. Reframed to a payment-status-aware set of states (`"Order Confirmed!"` / `"Payment Submitted"` / `"Payment Window Expired"` / `"Complete Your Payment"`) so the page never claims an unpaid order was simply "received."

**A real, pre-existing test-authoring bug surfaced while verifying this for real** (unlike the Razorpay version, which never got far enough to hit it, since the "Continue to Payment" button was unreachable without real Razorpay test credentials): `signed-in-checkout.spec.ts`'s full-checkout test read the `/api/orders` POST response body via `await orderResponse.text()` inside an `expect(..., message)` call's message argument - that argument is a plain JS expression and gets evaluated eagerly every time the line runs, pass or fail, so it silently consumed the response stream before the `.json()` call two lines later ever ran. Confirmed directly with a standalone debug script that the real root cause is actually one level worse: `checkout/page.tsx`'s own `window.location.href` navigation (a separate, pre-existing, deliberately-untouched lint issue - see BACKLOG.md) fires the instant its own fetch resolves and reliably wins the race against Playwright's CDP body-fetch regardless of ordering - reading the body via *either* `.text()` or `.json()`, as the very next statement after the response arrives, still throws "Response body is not available for a response that was navigated away from." Fixed by not reading the response body at all: asserting on `orderResponse.status()` alone, and verifying the order's real `paymentMethod` from `localStorage.getItem("stickhive:last-order")` (written synchronously by `handlePlaceOrder()` before it navigates) and from order-success's own rendered UI instead - both unaffected by the navigation race.

**Verified via**: full pre-push gate (`tsc --noEmit`, `next build`, `build:vinext`, `eslint` on touched files, `test:unit` - 26/26) clean. Unlike the Razorpay version, `STICKHIVE_UPI_ID`/`STICKHIVE_UPI_NAME` were already set in `.dev.vars`, so the full checkout-to-payment flow was verified end to end for real this time, not just up to a correctly-disabled button: signed in, added an item, filled the form, confirmed the payment card reads "UPI" (not Razorpay), placed the order, confirmed a real 201 and the order's real `paymentMethod` of `"upi"` (via the localStorage fix above), and confirmed `order-success` renders the "Pay ₹... via UPI" QR/deep-link section immediately with "Complete Your Payment" copy - not "Order Received", not a Razorpay button. `npx playwright test` run at both default and reduced concurrency to separate real failures from this repo's own already-documented load-induced flakiness (unrelated, untouched files like `custom-sticker.spec.ts` flipped pass/fail with concurrency alone in the full run; all touched specs passed reliably at `--workers=2`). `mobile-safari`'s coverage of checkout remains the known, pre-existing WebKit-secure-cookie gap already on record (unrelated to the UPI/Razorpay correction itself - the sign-in requirement is what widened it, not the payment method chosen).

## 2026-10-02 — Checkout: sign-in required, Razorpay-only, auto-launched payment

Three changes, all from the same realization: checkout's own "Verify Email To Continue" OTP step was never a separate verification - it called the exact same `requestEmailOtp`/`verifyEmailOtp` functions (`backend/auth/service.ts`) as the navbar's sign-in flow, just through a second URL (`/api/send-email-otp`, `/api/verify-email-otp`) that existed only as a compatibility adapter (`backend/README.md`'s own words: "retained as compatibility adapters for the current frontend"). A shopper verifying their email at checkout was, mechanically, signing in - just without the account state that normally comes with it.

1. **Checkout now requires an actual signed-in session.** `checkout/page.tsx` reads `useAuth()`; a guest sees a "Sign in to checkout" gate (reusing the existing navbar sign-in dialog via `window.__stickHiveOpenAuth`) instead of the form at all. The email field in `customer-form.tsx` is now `readOnly`/`disabled`, always showing the session's own address - never re-entered, never re-verified. The two compatibility-adapter routes (`/api/send-email-otp`, `/api/verify-email-otp`) are deleted outright now that nothing calls them - confirmed via grep across the whole repo (app code, tests, docs) before deleting, only `backend/README.md`'s own historical description referenced them, updated to say so.
2. **UPI (the hand-rolled QR-code-and-manual-admin-verification flow) is removed from checkout.** Razorpay is the only payment method shown - it already offers UPI apps, cards, and netbanking inside its own checkout, confirmed automatically via its signed webhook, so the manual-verification path it was supposedly a fallback for was redundant with what Razorpay already does, just slower and reliant on an admin being available. `paymentMethod` is now a literal `"razorpay"` constant, not state; when Razorpay isn't configured (`isRazorpayConfigured()` false), checkout shows "Payments are temporarily unavailable" rather than falling back to UPI - there's deliberately no fallback left to fall back to.
3. **Placing an order now launches the Razorpay payment portal automatically.** `order-success/page.tsx` had a manual "Pay Now" step after landing; a new ref-guarded `useEffect` calls the existing `handlePayWithRazorpay()` the moment the order and Razorpay's `checkout.js` are both ready, for a fresh (`not paid`, `not cancelled`) Razorpay order - removing a now-pointless extra click. The order is still only "confirmed" once the signed webhook marks it paid (unchanged); the page's copy was updated ("Complete Your Payment" / "The secure payment window should open automatically") so a shopper isn't left reading "Order Received" while a payment popup they weren't expecting opens over it.

**Verified via**: full pre-push gate (`tsc --noEmit`, `next build`, `build:vinext`, `eslint` on touched files, `test:unit` - 26/26) clean against this repo's own toolchain (this change arrived as a patch from a separate session that could only partially run its own gate - no `.dev.vars` there at all). `npx playwright test`, run multiple times at both default and reduced concurrency to separate real failures from this repo's own already-documented load-induced flakiness (confirmed by re-running the same specs at `--workers=1`/`--workers=2` and watching unrelated, untouched files like `custom-sticker.spec.ts` and `public-pages.spec.ts` flip between pass/fail purely with concurrency - a pattern already on record in BACKLOG.md from earlier sessions, not something this change caused):

No `RAZORPAY_KEY_ID`/`RAZORPAY_KEY_SECRET` test credentials were available in this environment; without them `isRazorpayConfigured()` is correctly `false` and checkout correctly shows "Payments Unavailable" - which is itself the correct, verified behavior for that state, but it means the one new end-to-end path this whole change exists to enable (Place Order → straight into Razorpay) has not been exercised for real. ## 2026-10-02 — Customer invoice redesign (`invoice-generator.ts`): real bugs fixed, not just a reskin

The ask was "make the invoice look good" - turned up several real, pre-existing bugs along the way, not just a visual pass:

- **The payment-status badge was hardcoded.** The original always rendered a green "PAYMENT CONFIRMED" badge regardless of the real `order.paymentStatus` it was handed - an unpaid, pending, or failed order's invoice still claimed the payment was confirmed. `paymentStatus`/`paymentVerification` were already threaded all the way through from `order-success/page.tsx`'s call site; the generator itself just never read them. Fixed with a real status→badge mapping (paid/pending/pending_confirmation/failed/cancelled/refunded), defaulting to "Payment Pending" (never a false "confirmed") for anything unexpected.
- **The QR code was always dead.** `public/dummy/payment-qr.png`, the image it loaded, is a 0-byte placeholder file - it always failed to load, so the QR section silently never rendered anything. Replaced with a real, generated QR (the `qrcode` package, already a project dependency for the UPI QR) encoding the order's actual `/track-order?orderId=...` page.
- **No timeout or error handling around image loads.** `loadImage()` had no `try/catch` around the canvas read and no timeout - a slow network request, or a cross-origin image whose host doesn't send CORS headers (`canvas.toDataURL()` throws on a "tainted" canvas), would leave the whole async `generateInvoice()` call hanging forever with zero feedback to the customer. Fixed with a 6s timeout and a try/catch that resolves `null` rather than throwing - used for the logo and now for each line item's product photo (new; the original never rendered item images in the table at all, despite `item.imageUrl` already being in its own type). A missing/failed photo falls back to a small drawn hexagon placeholder rather than a blank gap.
- **No page-break safety.** The original had no guard for the totals/QR/footer block running past the bottom margin - a long order, or one with wrapped item details, could push them off the page edge. Added: if the table's `finalY` lands past a safe threshold, start a fresh page (re-filling the cream background) before drawing the totals block. Verified with a 22-item order that genuinely spans 3 pages - table continuation correctly re-applies the brand background and a "(continued)" label on page 2, totals/QR/footer cleanly land on page 3 rather than overlapping or running off any of them.
- **The logo was embedded at full resolution.** `doc.addImage()` embeds whatever pixel data it's handed as-is - it doesn't resample to the PDF display size. The brand logo is a 1024x1024 source PNG; embedding it unresized for an 18mm-wide placement alone made a 3-item test invoice ~4.9MB. `loadImage()` now downsamples onto a capped canvas (240px max dimension) before handing it to jsPDF - the same 3-item invoice came down to ~775KB. Kept PNG (not JPEG) throughout since product photos can have real transparency (die-cut stickers) that JPEG can't represent.
- Colors/typography now use the real site palette (`src/app/globals.css`'s `:root` vars - hive-yellow/honey-orange/honey-dash/cream/mint) instead of the original's own invented hex values, and the real support address (`hello@stickhive.com`, same as the footer/contact page) instead of no contact line at all.
- `order-success/page.tsx`'s "Download Invoice" button previously fired `generateInvoice()` with no loading state and no error handling at all (a thrown rejection just vanished into an unhandled promise). Now shows a spinner + disabled state while generating, and a real inline error message (matching the file's existing `razorpayError` pattern) if it fails.
- `(doc as any).lastAutoTable.finalY` is kept, now properly typed (`AutoTableJsPDF`) instead of cast to `any` - confirmed this is in fact the only way to read it with jspdf-autotable's functional API (`autoTable(doc, options)`); `applyPlugin`/`getLastAutoTable()` turned out to be a different, internal-only code path that doesn't expose this on a plain `jsPDF` instance - tried it first, got a runtime `TypeError`, traced it to jspdf-autotable's own source before reverting.

**Verified via**: a standalone esbuild bundle of the real `invoice-generator.ts` (plus its actual npm dependencies) driven by Playwright against a local static server, not just reads - three real scenarios rendered and inspected as actual PDFs: a paid order (badge, UPI ref detail, 2 real + 1 deliberately-broken product image all render correctly, including the hex-placeholder fallback), a pending order (confirms the badge bug is actually fixed, not just themed differently), and a 22-item order (confirms the 3-page break behavior). Full pre-push gate (`tsc --noEmit`, `next build`, `build:vinext`, `eslint` on touched files, `test:unit`) clean. New pre-existing lint debt surfaced while linting the touched file (not introduced by this change, confirmed via `git diff`) logged in BACKLOG.md rather than folded in here.

- **`src/components/products/product-grid.tsx` and its sibling `src/components/products/product-data.ts`** - a separate, unrelated, fully orphaned array/component with zero importers anywhere (confirmed via grep before deleting) - deleted outright. ## 2026-09-30 — Production-build e2e infrastructure (Tasks 4.2/4.3): five real bugs found, one HTTPS fix tried and reverted

Switching the e2e suite's default `webServer` from a manually-started `next dev` to a real `vinext build` + `wrangler dev` (local D1/R2, genuine `NODE_ENV=production`) was the actual Task 4.3 ask, and adding `POST /api/dev/mint-session` (dev-only, `AUTH_TEST_SESSION_SEAM=true`-gated) plus `signed-in-checkout.spec.ts` was Task 4.2. Both were straightforward. What took the rest of this pass was that running the *existing* suite against a genuinely production-equivalent server - rather than `next dev`'s no-op `cloudflare:workers` shim - surfaced several real, pre-existing issues that a less-realistic test server had been silently hiding:

- **`src/app/admin/[accessKey]/page.tsx` leaked a 200 on a wrong admin key.** `redirect("/404")` is a 307 to a page that itself renders 200 - `api-security.spec.ts`'s "does not leak order data without auth" check only ever caught this once it ran against a server where the redirect's target page is reachable at all status-wise. Fixed to `notFound()`, the same pattern `src/app/dev/layout.tsx` already used correctly.
- **`next.config.ts`'s `headers()` never matched the bare root.** `source: "/:path*"` matched every other route (confirmed via a systematic curl sweep: `/shop`, `/checkout`, `/custom-sticker`, `/wishlist`, `/my-addresses`, `/about`, `/contact`, even a 404 - all correct) but not `/` itself, on both the local build and the real live site. This is a vinext matcher gap, not an app bug. Fixed with a dedicated `source: "/"` rule rather than chasing why the general matcher misses the zero-segment case.
