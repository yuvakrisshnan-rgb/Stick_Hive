Picking this session back up after a context-compaction boundary, `git status` showed 13 modified/new files - `src/app/shop/page.tsx`, `src/app/shop/[id]/page.tsx`, `backend/products/service.ts` (new), `shop-catalog.tsx`, `product-details.tsx`, `related-products.tsx`, the `/dev/product-preview` files, `next.config.ts` - all uncommitted, all implementing the D1-backed shop rewire the task list asked for. The compaction summary I'd been given said Task 3 was "Not started" - that was wrong; the working tree, not the summary, is ground truth, and I went with what `git status`/`git diff` actually showed.

**Verified via**: `git status --short` (13 modified/untracked files, none in any of the 5 commits already on the branch) and `git diff` on each (clean, well-formed - `ProductDetails`/`RelatedProducts` converted from importing the static `PRODUCTS` array to receiving `allProducts` as a prop, so both a D1 and a static call site can supply their own list).

**What was missing**: the task list's explicit requirement - "keep the static array as a flag-gated fallback until verified" - hadn't been implemented. `shop/page.tsx` called `listActiveProducts()` (D1) unconditionally, no fallback. Two concrete failures from this:
- `npm run build` failed outright: `Error: D1 binding "DB" is not configured` while prerendering `/shop` - D1 only exists at request time inside the real Workers runtime, never during `next build`'s static generation step.
- Plain `npm run dev` (no Workers runtime; `cloudflare:workers` resolves to the no-op shim) 500'd on every `/shop` request for the same reason - confirmed by curl and the dev server's own error log.

Remote D1 also isn't in a state to serve this yet regardless of local behavior: only `migrations/0006_products.sql` (schema) and the local seed (194 rows, 107 active) have run - the remote migration, the remote seed, and the R2 image upload are all still unexecuted per the standing "stop before remote D1 writes / real R2 changes" rule (see DEPLOY_CHECKLIST.md). Flipping the live shop to D1 right now, even if the build didn't fail, would serve an empty or erroring shop in production.

**Fix**: `backend/products/catalog.ts` (new) - `listShopProducts()`/`getShopProductBySlug()` wrap the D1 service and gate on `process.env.PRODUCTS_SOURCE === "d1"`, defaulting to the static array when unset. Even with the flag on, a D1 read failure is caught and falls back to static rather than 500ing the shop. `shop/page.tsx` and `shop/[id]/page.tsx` now call the wrapper and are marked `export const dynamic = "force-dynamic"` so `next build` never attempts to prerender them against D1 at all. Default (flag unset) is what ships until the remote steps in DEPLOY_CHECKLIST.md have actually run and been verified.

**Verified via**: `npm run build` (was failing on `/shop`, now completes, `/shop` and `/shop/[id]` both classified `ƒ Dynamic`), `npm run build:vinext` (completes), and a live curl of `/shop` under plain `next dev` (was 500, now 200 and renders the static array's products).

## 2026-09-21 — Bug hunt (Task 2): findings and fixes

Full `npx playwright test` run started at 27/74 failing. Two classes of cause, both real, neither the app's live-shop content:

1. **Dev-server compile contention, not app bugs.** The first couple of full-suite runs (4 parallel workers against a single `next dev` process) threw ~30s timeouts on ordinary actions (clicking "Add to Cart", `page.goto("/checkout")`). Re-running the same specs with `--workers=1` turned 14 timeouts into 5 fast (<20s), deterministic failures - confirming the timeouts were Turbopack on-demand-compile contention across concurrent workers hitting cold routes, not real waits. The e2e suite has no `webServer`/prod-build config in `playwright.config.ts`; running it against `next build && next start` instead of `next dev` would remove this class of flakiness structurally - not done here (out of scope), noted in BACKLOG.md.

2. **Real, fixed bugs** (all local, all pushed with this session's other work):
   - **CSP blocked the PIN-code lookup.** `next.config.ts`'s `connect-src` never allowlisted `api.postalpincode.in`, so the checkout form's browser-side `fetch` to it was silently CSP-blocked; `lookupPincode()`'s catch swallowed the failure into a generic "check your connection" message. Nobody's PIN code has ever auto-filled city/state in an environment where this CSP is actually enforced. Fixed by adding the host to `connect-src`. Verified live (curl to the real API returns 200; the browser fetch failed only under CSP; auto-fill test passes after the fix, fails before it).
   - **Nearly the entire static demo catalogue had broken images.** 29 of 30 static products (`src/lib/product-data.ts`) pointed at `/stickers/*.png` files that never existed in this repo (`find`/`git log --diff-filter=A` across the whole history: zero matches - not a deletion, never committed). Every `<Image>` render 400'd via Next's image optimizer. `StickerImage` (`sticker-image.tsx`) already had the right `product.image ? <Image/> : <emoji>` fallback and was unaffected once `image` was undefined; `cart-drawer.tsx`'s `CartItem`/`CustomCartItem` did not have that fallback (referenced an equally-nonexistent `/placeholder-sticker.png`) and was fixed to match the same convention. Fix: stripped the 27 dead `.png` references from `product-data.ts` (kept the 3 that reference real, existing `.svg` files - `mini-anime-pack`, `level-up`, `tiny-bot`). This is a real, pre-existing content gap, not a regression from this session - and it's exactly the gap the D1+R2 product pipeline (this session's whole body of work) exists to close. No fabricated artwork was generated to fill it.
   - **`/api/admin/orders/[orderId]/route.ts` has no GET handler** (only `PATCH`) - the test expected 401/404 on a GET, got Next's own framework-level 405. Not a leak (405 carries no data either way) and not new. Widened the expectation to include 405.
   - **Rate-limit bucket sharing across parallel tests.** Several `api-security.spec.ts` tests share the default `127.0.0.1` bucket with tests elsewhere in the same file that deliberately trip the send-otp cooldown; `fullyParallel` doesn't guarantee ordering, so a 400-expecting test could get 429 if a cooldown test ran first. Fixed the same way the file's own malformed-body tests already did: each sends its own `x-forwarded-for`.
   - **Cart drawer is (correctly, deliberately) auth-gated** - `cart-drawer.tsx`'s own comment documents this as intentional ("Your Stick Hive cart is tied to your account so only you can see it"), matching the `/orders` and `/account/settings` pattern. The old `cart-checkout.spec.ts` "Cart" tests assumed a guest could see cart contents and a checkout link directly - never true once this shipped. Rewrote them to assert the actual guest UX (sign-in prompt) instead of building a test-only auth bypass (would mean reimplementing `backend/auth/crypto.ts`'s session signing in the test harness - a real, separate test-infra gap, not solved here; see BACKLOG.md).
   - **Several `getByLabel`/`getByRole` locators were unscoped** and matched the site-wide footer's own email input/mailto link, or (for "Verify Email To Continue") a Razorpay payment-method button whose name also matched a loose `/verify email|pay/i` alternation. Added `data-testid="checkout-form"` to `customer-form.tsx`'s root section and scoped the checkout-field locators to it; the payment/verify button lives in `checkout/page.tsx` itself, outside that section, so it's matched by its own precise name instead.
   - **PIN-doesn't-exist test used `"000000"`**, which fails PIN *format* validation (`/^[1-9]\d{5}$/`) before the lookup ever runs, so it could never reach the "doesn't exist" message it was asserting for. Swapped to `"999999"` (format-valid, confirmed against the live India Post API to return `Status: "Error"`, `"No records found"`).
   - **About-page copy assertion never matched real copy.** Test expected `/from a classroom idea/i`; the page's actual text (`src/app/about/page.tsx:227`) is "began as a classroom idea" - no "from". Loosened the regex to match the real, current copy rather than editing site copy to satisfy an arbitrary test string.
   - **Homepage console-error assertion couldn't pass under dev**, full stop: `next.config.ts`'s CSP deliberately omits `'unsafe-eval'` (documented there - a real, intentional XSS-surface trade-off), and the unavoidable, dev-only, production-safe side effect is React logging `"eval() is not supported..."` on every page load (its own text: "React will never use eval() in production mode"). Filtered this one specific, known message out of the test's error collection rather than weakening the CSP or asserting against a message this suite can never keep clean under `next dev`.
   - **Mobile-only: adding text opens a bottom-sheet properties panel that covers the toolbar**, including Undo/Redo, on a mobile viewport (`sticker-editor-shell.tsx`) - a real mobile user hits the same problem. The panel's small visible "X" close button had no accessible name at all (icon-only, no `aria-label`), so it couldn't be targeted directly; added `aria-label="Close panel and deselect"` to it (and `"Minimize panel"` to its chevron sibling) and updated the test to close the panel before using Undo/Redo, matching real mobile use.

**Left as pre-existing, out of scope for this pass** (confirmed via `git diff` that none of it is on lines this session touched): `react-hooks/set-state-in-effect` errors in `shop-catalog.tsx` (`setSearch(urlSearch)` in a bare `useEffect`) and `sticker-editor-shell.tsx` (`setSheetExpanded(true)` in a bare `useEffect`); two `@typescript-eslint/no-explicit-any` errors in `customer-form.tsx` (lines 255, 292); a `no-location-assign-relative-destination` warning and two `no-unused-expressions` warnings in `cart-drawer.tsx`. Tracked in BACKLOG.md as a dedicated lint pass, per Task 2's own framing ("lint (worst files first)") rather than folded into unrelated fixes here.

**Verified via**: full `npx playwright test` (both `chromium` and `mobile-safari` projects) - 74/74 passing after all of the above; `npm run test:unit` - 13/13 passing throughout, untouched by any of this.

## 2026-09-21 — Category union: extend with no lossy merges

Decision: add all CSV categories that don't already exactly match an existing `Category` union value, using their exact source strings — not renamed, not collapsed into a similar-sounding existing value.

- `Anime` — already an exact match, no new value needed.
- `Bollywood`, `BTS`, `flower stickers`, `Meme stickers`, `Rick and Morty`, `Stickers with dialogues` — added verbatim.

Earlier (before this was escalated to "decide it yourself, no lossy merges") I'd proposed collapsing `Rick and Morty`→`Series`, `flower stickers`→`Nature`, `Stickers with dialogues`→`Memes`, and `BTS`→a generic `K-Pop`. Explicitly overridden by this instruction: the union now has to be lossless against what's actually stored in D1/CSV, since a lossy mapping would just force a translation layer back into existence at every consumer — the opposite of the point.

**Known cosmetic side effect**: this makes the union casing/spacing inconsistent (`"Nature"` Title-Case single-word vs. `"flower stickers"` lowercase-with-space) rather than normalizing everything to one style. Deliberate — exact fidelity to the real stored strings over cosmetic uniformity.
