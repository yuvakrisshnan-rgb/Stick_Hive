## Test infrastructure

**2026-09-30 - both items below are done, Tasks 4.2/4.3, with one known remaining gap.** `POST /api/dev/mint-session` (`backend/auth/service.ts`'s `mintTestSession`, gated on `AUTH_TEST_SESSION_SEAM=true` - set in `.dev.vars` only, never in `wrangler.jsonc`'s committed vars) mints a real session without the OTP round-trip; `tests/e2e/signed-in-checkout.spec.ts` uses it for real signed-in cart/checkout coverage. `playwright.config.ts`'s `webServer` now runs `vinext build` + `wrangler dev` (real Workers runtime, local D1/R2, on port 8787, plain HTTP) instead of relying on a manually-started `next dev`.

Non-obvious things that fell out of actually doing this, each worth knowing before touching this setup again:
- The production build genuinely runs with `NODE_ENV=production` (confirmed: `/dev/*` pages 404 there, matching real prod). Two existing `AUTH_DEBUG_OTP` gates in `backend/auth/service.ts` used to *also* require `NODE_ENV !== "production"`, which made them silently unreachable here - fixed to gate on `AUTH_DEBUG_OTP=true` alone (the committed `wrangler.jsonc` value, `"false"`, is the real safety boundary, not `NODE_ENV`).
- `getClientIp()` only trusts `CF-Connecting-IP` in production (correctly - `X-Forwarded-For` is trivially spoofable in real Cloudflare-routed traffic). With no real Cloudflare edge in front of a local `wrangler dev`, every unauthenticated request collapsed into one shared `UNKNOWN_CLIENT_IP` bucket (cap: 3 total). `api-security.spec.ts`'s existing per-test IP isolation used `X-Forwarded-For` - switched to `CF-Connecting-IP` everywhere in that file, and `signed-in-checkout.spec.ts` sets its own via `context.setExtraHTTPHeaders`.
- **Known gap, deliberately not fixed**: session cookies set `secure: NODE_ENV === "production"` (correct for the real HTTPS deployment) - over this local server's plain HTTP, that silently breaks WebKit specifically for anything needing a real signed-in session (Chromium has an undocumented "Secure cookies work on localhost over HTTP anyway" exception that WebKit doesn't implement, so a mint-session cookie is set but never sent back on mobile-safari - confirmed directly, not assumed). The correct-in-principle fix (`wrangler dev --local-protocol https`, a real if self-signed TLS listener) was tried and reverted: it measurably destabilized the rest of the suite under full parallel load (21 failures vs. 11 on plain http, including previously-solid tests like `custom-sticker.spec.ts`), a worse trade than the one bug it fixed - and it didn't even fully fix that bug (mobile-safari's signed-in checkout still failed, just differently). `signed-in-checkout.spec.ts`'s coverage is therefore real and passing on chromium only; mobile-safari is a known, understood gap, not a mystery to debug blind next time. A real fix likely needs either a trusted local CA cert (no browser-engine special-casing needed) or accepting `reuseExistingServer`/lower parallelism specifically for HTTPS runs - not investigated further here.
- **2026-10-02 - this gap's blast radius just widened.** Checkout now requires a real signed-in session unconditionally (see DECISIONS.md's checkout sign-in/payment-method entries) - previously only `signed-in-checkout.spec.ts`'s own tests needed one. - **2026-10-02 - resolved, Razorpay reverted to direct UPI.** The payment method this checkout work targets changed from Razorpay back to direct UPI (QR code + deep link, no gateway) - see DECISIONS.md. `signed-in-checkout.spec.ts`'s full-checkout test is now verified end to end for real, locally (`STICKHIVE_UPI_ID` was already set in `.dev.vars`, so no credentials gap this time, unlike Razorpay's). ## Security headers were missing on the homepage specifically - fixed (2026-09-30)

Found while investigating an `api-security.spec.ts` failure that only surfaced once the suite ran against a real production build (Task 4.3) instead of `next dev`. Initially looked like a blanket "page routes don't get headers" gap, but a systematic curl sweep (`/`, `/shop`, `/checkout`, `/custom-sticker`, `/wishlist`, `/my-addresses`, `/about`, `/contact`, even a 404) showed **every one of those routes correctly carried the headers except the bare root `/`** - both on the local production build and the real live site. Root cause: `next.config.ts`'s `headers()` rule used `source: "/:path*"`, and vinext's matcher for that pattern doesn't resolve the zero-segment case (the bare root) the way Next.js's own path-to-regexp-based matcher does - so the rule silently never matched `/` itself, only `/anything`. Fixed with a dedicated `source: "/"` rule carrying the same header set (`next.config.ts`, right after the general rule) - confirmed via curl against a fresh local production build that `/` now carries the full header set identically to every other route.

**Still outstanding**: this fix is local-only until the next deploy - the live site (`stickhive.yuvakrisshnan.workers.dev`) still serves `/` with no security headers until this change ships.

## R2 public image domain serves HTTP/1.1, not HTTP/2 (DNS/bucket change, not code)

Confirmed via `curl -w "%{http_version}"` against `pub-8a6c62ba68f94cc09c8327319bffa53c.r2.dev`: it's HTTP/1.1. Browsers cap concurrent connections per origin at ~6 under HTTP/1.1, so sticker images queue in batches of 6 behind a single shared origin on `/shop` - independent of the pagination fix (2026-09-25) that bounds how many images compete for those slots per page. A single warmed-up fetch of one image still took ~600ms TTFB on its own, so there's real per-request latency here too, not just queueing.

Fix: route R2's public bucket through a custom domain on Cloudflare's own zone instead of the `*.r2.dev` dev domain - that would serve HTTP/2+ (or HTTP/3) and let images load in parallel instead of queuing. This is a Cloudflare dashboard/DNS + bucket-binding change (R2 bucket → custom domain, zone proxied), not application code - worth doing, but deliberately not bundled into the pagination fix.
